## 3. 必须澄清与待评审

本轮没有新发现必须让用户重答的商品业务问题。阶段尚未关闭的原因是**v0.11 增量范围及推荐开发路径尚待用户评审**，不是已知需求缺失。

当前建议一次核对三项：

1. 已整理的对话创作、自由节点、中途开始和保留项是否准确。
2. 首批以“自由节点基础＋真实对话脚本上画布”为闭环，随后再扩图片／视频／成片，是否符合优先级。
3. 在本对话统筹前后端并行，产品内先用一个主控 Agent＋专业能力，是否接受作为实施方向。

具体面板宽度、引用控件形式、版本如何呈现属于原型／技术适配项，不强迫用户先决定数据库、API 名称、队列等技术细节。按代表页可审阅结果收敛，不再重复询问已经确定的 C 版主题、设置同比缩放和纯拼接规则。

新增付费验证仍需具体用例及预算核对；本次只做文档，无真实模型调用，相关支出不发生。不能提前要求用户给一个无限制预算，也不能把之前单次验收预算当作新范围授权。

## 5. 开发并行与阶段纪律

通用技术栈手册第一节明确：当人工确认、画布、多轮交互本身是核心能力时，可以“在一个阶段内同时做最小后端能力和最小真实交互”。因此本项目适合纵向切片，不必先写完所有后端才动前端，也不一次铺开整版界面。

主控维护 PRD、契约、公共类型和迁移；前端／后端分别实现不同文件；主控统一合并、服务操作、业务库迁移和付费测试。前端可用固定响应开发状态，但不得把它当作真实模型验收。每切片仍需实际联调、恢复与失败测试、浏览器检查和真实样例记录。

两份 Skill 不要求用户再建一个对话。用户可以选择另建，但推荐当前对话内部协作，以同一版本的需求／契约交付，减少用户转述和协调。
