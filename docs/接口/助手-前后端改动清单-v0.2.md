日期：2026-10-24｜状态：**待核对，未开发**
对应：PRD v0.9 §13、《助手系统提示词与行为规则-v0.2草案》、接口契约 v5.1

## 0. v0.1 → v0.2 修订要点

| # | 复核意见 | 本版改法 |
| --- | --- | --- |
| 1 | 仅优化提示词也应是完整交付 | 助手侧新增"模式 A"分支：只返回提示词，**不触发** estimate/submit；前后端均不强制模板 |
| 2 | 看图矛盾、事实不能靠假设 | 首版无视觉；后端不把图片字节传给 LLM；产品事实仅来自用户文本；示例标为设计示意 |
| 3 | 报价 ≠ 人工确认 | 反驳"token 即批准"：新增**两阶段**——报价单（仅报价）→ 用户确认（服务端批准）→ 提交（校验批准）；来源由后端写 |
| 4 | 限制不能波及原工作台 | 所有上限放进 `assistant` 命名空间，只作用于助手路径；手动 `/api/tasks` 行为不变 |
| 5 | 待确认分类 | 见 §7：产品必须确定 / 开发默认推荐 / 商业化后续 |

## 1. 一句话架构

```
前端助手侧栏 ──► 后端助手代理（新增） ──► LLM 适配层（新增，厂商无关）
                        │
                        ├─► 工具执行器（薄封装现有函数）
                        └─► 批准状态存储（新增，最小实现）
                                  │
                                  ▼
                        现有 tasks / estimate / templates / assets / drafts
```

原则：**模型只提议，后端做决定**。价格、可用性、参数合法性、额度、用户确认均由后端判定。

## 2. 后端改动范围

### 2.1 必须新增

| # | 能力 | 说明 | 依赖 |
| --- | --- | --- | --- |
| B1 | `POST /api/assistant/chat` | 助手唯一入口；后端持 Key；带会话 ID；**不做流式**（首版） | P1、D1 |
| B2 | `assistant/provider.py` 适配层 | 厂商无关：`chat(messages, tools) → tool_calls`；便于换型 | P1 |
| B3 | `assistant/tools.py` 工具执行器 | 薄封装现有函数：models/templates/assets/estimate/submit/get_task/cancel **+ confirm（见 B5）** | 现有代码 |
| B4 | **报价单（quote）记录** | `estimate` 在助手路径写入报价快照：`quote_id`、方案哈希、会话/项目、有效期；**不可用于提交** | — |
| B5 | **`POST /api/assistant/confirm`** | 用户**在界面上**确认后调用；校验 `quote_id` + 方案哈希一致 → 写**批准**（`approval_id`，一次性，绑定会话/项目/有效期） | B4 + 前端确认按钮 |
| B6 | 提交校验 | 助手路径提交必须带 `approval_id`；校验方案哈希、有效期、未使用、与会话一致；**不使用即拒** | B5 |

| B8 | 助手限流（独立命名空间） | 提问数、会话轮次、单轮工具数、会话 token/费用上限；**只作用于助手** | D3 |
| B9 | 助手用量记录 | 每轮记录 input/output token、工具调用次数、拒答原因；**与生成用量分开存储** | — |
| B10 | 审计日志 | 报价→确认→提交三段可追溯（谁、何时、哪个方案） | — |

## 4. 候选契约（草案，未实现）

> 仅为对齐字段，不是现有契约的一部分。

### 4.1 报价（复用并扩展 estimate）

```json
POST /api/tasks/estimate      // 现有接口，助手路径复用
{ "kind": "video", "model_id": "<当前可用视频模型>",
  "input_asset_id": "asset_…", "template_id": "tpl_product_motion_5s",
  "template_fields": { "motion": "推近特写", "duration": 5, "ratio": "9:16" } }
```

响应增加（v0.2 建议）：

```json
{ "estimated_cost_cny": 0.4536, "effective": { "duration": 5, "ratio": "9:16", "resolution": "720p" },
  "quote_id": "q_20261024_0001",
  "quote_binding": { "plan_hash": "sha256:…", "expires_in_s": 600 } }
```

> `quote_id` **只能**用于申请确认，**不能**用于提交。

### 4.2 用户确认（新增）

```json
POST /api/assistant/confirm
{ "session_id": "asst-20261024-0001", "quote_id": "q_20261024_0001",
  "project_id": "draft_xxx", "user_action": "confirm_generate" }
```

响应：

```json
{ "approval_id": "ap_20261024_0001", "plan_hash": "sha256:…",
  "expires_in_s": 600, "max_uses": 1 }
```

错误：

```json
{"error":{"code":"QUOTE_NOT_FOUND","message":"报价不存在或已过期，请重新报价"}}
{"error":{"code":"QUOTE_PLAN_MISMATCH","message":"方案已变更，请重新报价并确认"}}
{"error":{"code":"APPROVAL_ALREADY_USED","message":"该确认已使用，请重新报价"}}
```

### 4.3 提交（现有接口 + 批准校验）

```json
POST /api/tasks
{ "…现有字段不变…", "approval_id": "ap_20261024_0001" }
```

服务端行为：

| 情况 | 结果 |
| --- | --- |
| `origin=assistant` 且校验通过 | 建任务；`approval_id` 置为已用；`client_request_id` 由批准派生 → 重复请求返回同一 task |
| `origin=assistant` 无 `approval_id` | 409 `CONFIRM_REQUIRED` |
| `origin=assistant` 方案哈希不一致 | 409 `APPROVAL_PLAN_MISMATCH` |
| `origin=assistant` 批准已用 | 返回**原任务**（幂等），不新建；若参数不同 → 409 |
| `origin=manual` | **不校验批准**，行为与当前完全一致 |

### 4.4 助手接口错误码（新增候选）

| code | HTTP | 说明 |
| --- | --- | --- |
| `ASSISTANT_UNAVAILABLE` | 503 | LLM 不可用，提示可改用直接操作 |
| `ASSISTANT_TURN_LIMIT` | 429 | 会话轮次/提问数超限（助手专属） |
| `ASSISTANT_TOOL_BUDGET` | 429 | 单轮工具调用超限 |
| `CONFIRM_REQUIRED` | 409 | 助手提交缺少批准 |
| `QUOTE_NOT_FOUND` / `QUOTE_PLAN_MISMATCH` | 409 | 报价缺失/过期/方案不一致 |
| `APPROVAL_PLAN_MISMATCH` / `APPROVAL_ALREADY_USED` | 409 | 批准与方案不符 / 已使用 |

## 5. 限制的归属（v0.2 明确）

| 限制 | 归属 | 是否影响手动操作 |
| --- | --- | --- |
| 提问数（建议 4） | 助手会话 | ❌ 不影响 |
| 会话轮次（建议 12） | 助手会话 | ❌ |
| 单轮工具数（建议 3） | 助手执行器 | ❌ |
| 会话 token/费用上限 | 助手会话 | ❌ |
| 助手侧重试 ≤1（建议） | 助手执行器 | ❌ 手动重试不变 |
| 预算闸门 `BUDGET_CNY` | 现有任务系统 | ✅ 两边都受约束（保持不变） |

> 新开会话只重置**会话级**计数，**不清零**工作区消耗与预算。

## 6. 计量（v0.2）

| 类别 | 记录内容 | 存储 | 现状 |
| --- | --- | --- | --- |
| 生成用量 | 任务 `cost_cny` / `usage_json` | 现有 `tasks` | ✅ 已实现（估算，非账单） |
| 助手用量 | 每轮 input/output token、工具次数 | 新表或日志（**待建**） | ❌ 未实现 |
| 统一积分 | 换算后的余额、预占、结算 | 账本（**待建**） | ❌ 未实现 |

- 两类用量**分别记录**，为后续统一换算留接口。
- **不得**展示虚构可消费余额；未建账本前只能显示"本次估算费用"。

## 7. 待确认（三档，附推荐）

### 7.1 产品必须确定（阻塞接入）

| # | 问题 | 推荐 | 理由 |
| --- | --- | --- | --- |
| P1 | 运行时 LLM 型号（厂商+型号+账号可用性） | 沿用火山方舟已开通文本模型 | 已有 Key/计费/时延；避免第二套账号与合规流程。需先确认真实可用与单价 |
| P2 | 首版是否启用看图 | **不启用** | 主场景不需要；避免图片出境与"识别错误被当事实" |
| P3 | 真实测试预算 | 单独小额批准（约 ¥10 内，仅 LLM token） | 助手测试不产生图片/视频费用 |

### 7.2 开发默认推荐（不阻塞）

| # | 问题 | 推荐 | 理由 |
| --- | --- | --- | --- |
| D1 | 流式显示 | 首版不做 | 回复短；降低代理与前端复杂度 |
| D2 | 会话/brief 存储 | brief 存草稿 `content`；消息前端内存 | 零新增表、零迁移 |
| D3 | 上限默认值 | 提问 4 / 轮次 12 / 单轮工具 3 / token 上限按成本换算 | 覆盖正常创作；可配置 |
| D4 | 超时 | 单轮 30s、工具 15s | 与生成轮询解耦 |
| D5 | 助手上限是否全局 | 仅助手；预算闸门仍全局限 | 不改变手动行为 |
| D6 | `quote_id` 是否对所有调用方返回 | 仅助手路径返回 | 避免给现有前端造成"必须确认"的错觉 |

### 7.3 商业化后续

统一积分方向已确认；**账本、余额、支付未实现**。换算率、会员权益、支付方式后续定；先分别记录两类用量。

## 8. 验收口径

| 项 | 判定 | 当前 |
| --- | --- | --- |
| 直接操作不受影响（A18） | 关闭助手后全流程可用，含取消/重试 | ⬜ |
| 仅优化即交付（A19） | 只要润色时无报价/无模板/无提交 | ⬜ |
| 不冒充看图（A21） | 回复无"图中是…"，事实可追溯 | ⬜ |
| 关键事实缺失即停（A22） | 输出待补充清单，不生成 | ⬜ |
| 报价≠确认（A23） | 无批准提交被拒 | ⬜ |
| 参数变更需重新确认（A24） | 旧批准失效 | ⬜ |
| 重复提交幂等（A25） | 返回同一 task | ⬜ |
| 来源不可伪造（A26） | 忽略模型传入 caller_id；手动路径不变 | ⬜ |

**不得**以"提示词已写好""接口已存在""负向测试通过"表述为验收完成。

## 9. 建议实施顺序（确认后）

1. 定 P1–P3（不写代码）。
2. 后端 B1–B3 + B7（代理、适配层、工具执行器、来源写入），用**假 LLM**（固定回复）跑通工具链与限流 → 免费可验证。
3. 后端 B4–B6（报价单、确认、批准校验）+ 幂等。
4. 前端 F1/F3/F4/F5/F6/F8/F11（侧栏、选项、模板卡、确认框、转直接操作、参数变更提示、移动端）。
5. 接入真实 LLM，跑 A19/A21/A23/A26 与违规用例集（人工抽检）。
6. 用量分别记录 → 积分账本（最后）。

每步最小验收均**免费可验证**；涉及真实生成的验证需单独批准预算。
