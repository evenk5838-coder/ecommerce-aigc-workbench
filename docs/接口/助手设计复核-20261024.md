# 可选创作助手设计复核

日期：2026-10-24。范围：助手提示词 v0.1、PRD v0.8 草案、助手前后端改动清单 v0.1。仅复核设计，没有修改产品代码、调用模型或运行生成任务。

## 本轮交付判断

本轮要求的设计产物已落盘：助手系统提示词与示例、现有 PRD 的增量修订、前后端改动范围。已写明保留直接操作、单 Agent、复用现有生成服务、无限画布 P2，以及 LLM/助手接口/积分账本未实现。

这说明设计任务已有交付，不代表助手功能已经可用；下面的修订应先回写草案，再作为开发依据。

## 需要修订

### 1. 仅优化提示词也应是完整交付

现有系统提示词将完整工作流程固定为选模板、预估、确认、提交。用户只请求润色时，应直接交付优化后的提示词并停止，不强制进入模板匹配、报价或生成。

只有用户希望平台执行生成时才进入报价与提交。无合适模板时，也应允许复用已有自由创作接口，不强行推荐模板。

### 2. 看图能力与示例须一致，事实不能靠假设补全

草案默认只给 LLM 文本与素材元数据，却在规则中使用“参考素材可见内容”，在示例中声称“图里现在是单瓶精华液”，还加入用户未明确要求的“标签空白区”。纯文本首版不能从文件尺寸、ID 或不可靠文件名推断商品外观与品类。

应改为“当前选中的商品图”；商品名称、数量、包装等来自用户确认的文本资料。若以后启用看图，应把识别结果与用户确认事实区分。示例须标明设计示意，不能称为真实工具输出。

四轮提问、一轮优化及一次重试等数值是草案建议，不能在项目状态里写成用户已确认。达到提问上限时，可提出待用户确认的创意默认值；关键商品事实或必需素材仍缺失时，应停在待补充状态，不可用假设补齐后生成。

### 3. 报价与人工确认是两个动作

estimate 签发的 token 只能证明报过价。若 token 直接进入 LLM 工具结果，助手能拿它立即 submit，因此不能仅靠“有 token”证明用户明确确认。

应描述清楚：报价先形成待确认方案；用户通过可信的确认操作产生服务端批准状态；执行时核对批准方案、会话/项目、有效期及是否已使用。模型改了参数须重新报价和确认，重复执行不能重复建任务。

助手来源由后端执行器确定，不信任模型传入的 caller_id；不能通过把 caller_id 改成 local 绕过确认。原有手动入口仍独立可用，不因新增助手门禁被迫进入对话。

### 4. 限制助手，不能顺带限制原工作台

“重试最多一次”“最多四次提问”等约束应明确是助手执行策略/建议默认配置，不可未经确认改成现有手动任务接口的全局限制。

澄清次数、对话总轮数、工具次数和费用上限是不同概念；限制其中一个不等于控制全部成本。“新开会话”不能清零用户/工作区总体消耗额度。首版可按本机使用范围做可配置限制，公开运营前再补可靠身份与额度归属。

### 5. 待确认问题按影响分类，避免再次变成重新立项

- 真正接入 LLM 前确定：产品运行时型号、账号是否可用、测试费用范围。
- 需要产品权衡：助手是否看图。纯文本可先写为推荐方案，说明用户须提供必要的商品描述，不冒充已有视觉理解。
- 工程推荐方案：是否流式、会话存哪里、超时与轮次上限。后端给简洁建议、理由与默认值，不把所有选择都变成产品经理必须逐项解答的门槛。
- 商业化后续：积分换算、会员权益、支付。统一积分方向已确认，正式换算与账本尚未完成；可先记录真实 LLM/生成用量，不能展示虚构可消费余额。

## 下一步

先在已有三份草案中修正以上内容，保留版本与原有功能，不新建平台、不实现助手代码、不新增付费调用。再收敛 LLM 与看图能力等必要产品选择，形成一次增量接口设计及前后端实施方案。
