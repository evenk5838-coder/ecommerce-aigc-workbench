## 2. 下一版 MVP 流程缺口与前后端分工

### 2.1 目标闭环（【已确认】用户期望）

```
开始创作 → 准备素材 → 设置与确认 → 生成 → 检查与修改 → 保存下载
```

### 2.2 当前覆盖 vs 缺口

| 环节 | 当前【已实现】 | 下一版缺口 |
| --- | --- | --- |
| 开始创作 | 生图/生视频 + 用途预设 | 无模板入口（工作模板/热点模板）；自由创作与模板入口关系未定 |
| 准备素材 | 单参考图上传/选择 + 提示词 | 缺"商品特征/不可改动要素"的结构化输入，仅靠提示词预设"不增删商品" |
| 设置与确认 | 比例/时长/数量 + 费用估算展示 | 无独立的"生成前确认"步骤；费用为估算、无预算预占与本次任务明细确认 |
| 生成 | 提交即付费，单 worker 排队 | 多模型下需"按任务/模板过滤兼容模型 + 切换时参数保留/提示不兼容" |
| 检查与修改 | 预览、复用为参考图/首帧/排版、重试 | 无"原图 vs 产物"对照审核；失败后的"下一步操作"指引可加强 |
| 保存下载 | 草稿、素材库、PNG/ZIP | 交付语义弱：产物未关联"模型/模板版本/原图/参数/任务"一键追溯；无按批次交付清单 |

**关键判断（【建议】）**：下一版 MVP 的完成度不应以"新增模型数量"衡量，而应以"一个真实用户能否独立走完闭环并产出可追溯、可交付的素材"衡量。

### 2.3 前端需要做什么（【建议】）

1. **模板入口**：选模板 → 渲染字段表单（商品图上传、文字字段）→ 带入默认参数 → 进入统一创作页。
2. **多模型选择**：按当前任务类型与模板兼容性过滤模型；切换模型时保留可复用输入（提示词/参考图/比例），明确标记不兼容参数并要求用户确认调整。
3. **生成前确认**：显示本次任务明细（模板/模型/规格/数量/费用估算或范围），用户确认后才提交。
4. **结果对照与追溯**：产物卡片显示实际模型、模板版本、原图、参数、费用；提供"复用为参考图/视频首帧/加入排版"及下载。
5. **错误与下一步**：基于后端错误码给出可执行提示（重试/改参数/人工对账），非仅展示原始错误。

### 2.4 后端需要做什么（【建议】）

1. **模型能力元数据**：结构化登记每个模型的输入方式、比例/分辨率、时长、价格、开通状态、provider，供 `/api/models` 返回并支撑前端过滤（见 §3.1）。
2. **模板存储与校验**：模板 CRUD + 稳定 `template_id`/`template_version` + 字段 schema + 输入校验（见 §3.2）。
3. **任务字段增量**：任务记录 `template_id`、`template_version`、`external_request_id`、`caller_id`（见 §3.3）。
4. **生成前确认支撑**：提交前返回可执行任务的明细与费用估算（或范围），预算校验保持在后端。
5. **交付追溯**：产物/任务关联元数据补全，使结果可按任务反查模型/模板/原图/参数。

## 3. 数据结构与接口改动建议（多模型 / 单次模板 / 跨项目 API 预留）

> 以下为**候选设计**，不冻结 URL 与字段。原则：优先复用现有 assets/tasks/batches/drafts 接口，只做增量。

### 3.1 多模型：模型能力发现

现状：`config.MODEL_REGISTRY`（Python dict）+ `MODEL_ACTIVATION`。`GET /api/models` 已返回 `kind/provider/downloaded/activation/max_size/default_size/note`。

【建议】增量：
- 将能力字段显式化：`input_modes`（text_to_image/image_to_image/i2v）、`ratios`（支持比例）、`resolutions`、`duration_s`（视频）、`pricing`（单价口径）、`params_schema`（允许参数与范围）。
- 数据形态二选一（【建议】先用 `config` 结构化 dict，暂不建表；待模板需持久化时再落库）：保持 Python 配置，保证 `/api/models` 输出稳定。
- 切换模型时参数保留规则：前端按 `params_schema` 判断兼容性，后端以 `params_schema` 做最终校验。

### 3.2 单次模板

【建议】新增表（或 JSON 文件起步，规模大后再落库）：

```
templates(
  id, template_id UNIQUE, template_version, kind(image|video),
  category(work|hot), name, description, status(active|deprecated),
  fields_json,          -- 填写字段 schema（上传字段/文本字段/选择字段）
  default_params_json,  -- 带入的默认生成参数
  compatible_models_json, -- 兼容模型约束（能力/比例/时长）
  created_at, updated_at
)
-- 模板版本：template_versions(template_id, version, snapshot_json, created_at)
```

- 稳定引用：任务只记 `template_id + template_version`，模板后续更新不影响历史任务追溯。
- 字段校验：后端按 `fields_json` 校验必填与类型，不把模板做成前端硬编码。
- 现有白底/氛围提示词预设**不等于**模板；模板是"字段 + 默认参数 + 兼容模型 + 版本"的完整对象。

### 3.3 跨项目 API 预留

【建议】对现有接口做**增量字段**，不另建平行系统：

| 能力 | 现状 | 增量建议 |
| --- | --- | --- |
| 能力发现 | `GET /api/models` | 扩展能力字段（§3.1）；【建议】新增 `GET /api/templates` 供调用方发现模板 |
| 模板引用 | 无 | `POST /api/tasks` 增 `template_id`/`template_version`；任务回显实际使用版本 |
| 素材交接 | `POST /api/assets` 本机无鉴权 | 上传/引用沿用 asset_id；**不传本机绝对路径**；访问经 `/api/assets/{id}/file` + 鉴权，按需加有效期/归属 |
| 异步生成 | `POST /api/tasks` → task_id，轮询 | 复用；结果返回 asset_id 与可访问方式 |
| 外部任务关联 | 无 | 任务增 `external_request_id`；调用方用 `client_request_id`（已有）做幂等 |
| 幂等 | `client_request_id` 已查重返回已有任务 | 保留；跨项目语义下 `external_request_id` 为调用方业务键，`client_request_id` 为幂等键，二者分开 |
| 结果契约 | 任务含 model_id/cost_cny/usage_json | 补 `template_version`、实际规格、费用口径（估算 vs 结算） |
| 鉴权限额 | 无 | 新增 API Key/Token 鉴权 + `caller_id` 归因到任务与用量；额度校验在创作平台后端，**不把供应商 Key 下发运营端** |
| 版本兼容 | 无 | URL 版本或 Accept 版本头 + 变更记录，字段只增不改 |

【建议】首版：**轮询**为候选，Webhook 暂缓（用户尚未决定，见 §6）。

### 3.4 明确不做（本轮）

- 不建立两个项目共享数据库的依赖。
- 不把本机文件路径当作远程素材地址。
- 不在运营工作台开发前宣称两产品已打通；只可做"测试调用方"验证。
