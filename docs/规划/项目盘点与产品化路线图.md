### 已知能力边界

- 无限节点创作画布、局部重绘/扩图、多SKU一致性保证、视频剪辑拼接、文生视频尚未实现或验收。
- 云端视频已经开始生成后，本地停止等待不保证云端停止或不计费。应保留真实语义，而不是把供应商限制当成可直接修好的前端功能。
- 云端“排队中成功取消”尚缺真实成功样本；已取得的409响应证明运行中取消边界，不能算排队取消成功。
- 同步图片调用遇到创建结果不明确时，不能按普通失败盲目重试；未来要补核对与人工处理路径。
- 当前SKU标签是项目内分组，没有正式商品主数据、跨项目品牌资产和团队协作。

### 本次代码核对发现的工程事项

| 事项 | 当前证据 | 后续动作 |
| --- | --- | --- |
| 缺正式版本仓库 | 当前目录 `git rev-parse` 返回非Git仓库；已有首版源码ZIP不是完整版本管理 | 建立仓库、忽略规则核查、当前版本标记与备份；远程发布单独决定 |
| 临时环境 | start.command仍可回退到`/private/tmp/.../venv`，依赖含本地推理组件 | 迁移到项目可复现环境，云端运行与历史本地模型解耦 |
| 并发配置不等于实际并发 | worker.start仅启动一个线程；CONCURRENCY用于状态展示，未据此创建worker池 | 不应仅改环境变量就宣称支持多并发；需实现调度并压测 |
| 批次原子性待补 | post_batch逐项创建，缺全批预校验/统一事务 | 明确“全批拒绝”或“部分成功”契约，验证中间项无效与重复请求 |
| 草稿并发写待加固 | 先读版本再更新；有顺序冲突验证，缺原子条件更新和并发竞态证明 | 使用原子版本检查/更新，加入双写测试，不混同于现有冲突UI已验证 |
| 成本不能用于企业结算 | 仅统计已写入任务的cost；未见任务费用预占/企业账本 | 独立估算、预占、结算、对账；取消后云端仍计费等情况须纳入 |
| 日界线 | spent_today按UTC日切分，界面称“今日” | 明确业务时区和账单周期并统一显示 |
| 数据归属 | assets.owner默认local；任务/草稿缺用户与组织归属，接口无用户鉴权依赖 | 开放客户前完成后端权限与隔离，不依靠隐藏按钮或CORS |

这些是静态核对发现的缺口/风险；本次没有通过破坏性测试复现所有故障，不把风险写成已发生的数据丢失。

## 4. 产品方向：兼容个人、小商家与团队，先验证共用任务

已确认：电商AIGC、图片与视频、个人项目继续发展。用户纠正了仅面向B端的表述：也服务个人和小商家，产品可To B、可To C，不按商业标签排除使用者。

暂定工作假设（待访谈确认）：共用的高频任务是“围绕真实商品图制作上新或活动素材”。入口按工作复杂度区分：个人/小商家快速生成并自查下载；团队在同一套能力上增加商品库、批量计划、共享审核和统一交付。小商家也可能需要批量，团队成员也需要快速生成，不能按账号类型锁死功能。

首批种子用户从实际可接触的人中选择。需同时记录不同使用者的需求，但第一轮验证不必覆盖所有人群。To B/To C是商业服务方式，不应变成界面上强迫用户选择的标签。

建议先验证的价值主张：**把真实商品资料变成可审核、可追溯、可批量交付的图片与短视频素材。**

需要回答：谁天天做这项工作、由自己还是别人审核、谁付钱、现有做法耗费多少人工、什么错误不能接受、哪些数据可以发给模型服务商。均为待研究内容，不预填结论或客户原话。

候选业务闭环：

```mermaid
flowchart LR
  A[商品资料与参考图] --> B[生产清单：用途/比例/数量]
  B --> C[参数与费用确认]
  C --> D[批量生成与状态追踪]
  D --> E[原图对比与人工审核]
  E -->|不通过：记录原因| B
  E -->|通过| F[排版/生成短视频]
  F --> G[复核与交付打包]
  G --> H[采纳/返工/时间/成本记录]
```

当前已覆盖其中生成、状态、基础排版和单素材导出；商品档案、审核、业务交付与效果回收还需要补齐。个人使用允许跳过团队审核，采用轻量对比、自查、下载路径；复杂生产计划和正式审核只在需要时展开。自动发布到电商平台不在首轮假设范围内。

无限节点画布是已提出的明确方向，保留在路线图中；建议先验证生产清单与审核闭环，再决定是否前移。它需要前后端共同开发，不能只做前端拖拽后宣称流程执行完成。

## 6. 评测从“能生成”升级为“能交付”

建议先建立小型、固定、带真实商品原图和要求的样例集。首轮可从约10个SKU起步，数量和品类由可获得的真实素材决定；这是建议样本规模，不是已完成测试。保持输入、提示词、模型ID/版本、参数、输出、耗时、用量、评分与失败原因一一对应。

| 指标 | 定义 | 数据来源 / 现状 |
| --- | --- | --- |
| 技术成功率 | 成功产出且文件可打开的任务数 / 有效提交任务数 | 任务与文件校验；现有样例不等于稳定成功率 |
| 首次采纳率 | 第一轮产物被业务审核通过的需求数 / 已审核需求数 | 需要人工审核状态与真实需求ID；尚未建立 |
| 商品保真 | 数量、结构、颜色、包装文字、Logo等逐项对照 | 人工复核为主；严重错误不得被美观分平均掉 |
| 视频可用性 | 商品不变形、动作/运镜符合要求、无明显闪烁/新增物体 | 按镜头与时间段记录问题；不把单条流畅当全场景可用 |
| 合格素材成本 | 对应任务的模型/重试等可归因成本 / 最终通过素材数 | 将生成成本与人工审核、返工成本分别列出；不混用旧估算与新账单 |
| 交付周期 | 需求确认至审核通过/打包交付的时间 | 与人工基线对比；模型耗时只是其中一段 |
| 稳定性 | 队列等待、端到端耗时、恢复成功率、重复创建率 | 样本够用后报告分位数；当前不宣称P95/SLA |
| 客户价值 | 实际采纳、使用频次、返工时间、付费意愿 | 试点记录；尚无数据，不编造节省比例或收入 |

先记录基线，再确定指标目标。模型版本、参数或工作流改变后，用同一批样例做回归；历史失败和更正记录保留。

## 7. 文档产出顺序

1. **现在**：项目盘点与路线图、全链路文档索引、当前状态与README统一。
2. **开发前**：真实需求与立项结论、需求池、下一版PRD、业务流程和验收标准。
3. **设计时**：交互说明、架构、数据模型、权限、接口、任务与费用策略。相互交叉核对后开发。
4. **开发中**：需求到代码/用例的追踪、接口变更、测试与评测证据、缺陷台账持续更新。
5. **试用前**：部署/回滚/恢复、操作手册、数据处理说明、发布说明与试点方案。
6. **试用后**：真实使用反馈、质量与成本复盘、商业验证、下一版本优先级。

PRD先于本轮功能开发；评测和操作手册随实现持续更新，最终验收时定版。不能先把未来测试报告写成“通过”，也不用等所有功能结束才整理文档。
